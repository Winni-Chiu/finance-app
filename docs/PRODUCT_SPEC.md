# 財務管家 APP 正式產品規格

- 文件狀態：正式產品規格（已確認需求）
- 版本：1.0
- 更新日期：2026-09-23
- 文件範圍：本文件記錄目前對話中已確認的產品需求與驗收條件。未曾決定的細節集中列於「待確認事項」，不得因此弱化或延後執行已確認需求。

## 1. 產品定位與原則

### 1.1 產品定位

財務管家 APP 專注於個人消費、信用卡帳單週期管理，以及使用者自訂消費統計。產品不以完整記帳軟體為目標，不要求提供完整資產、負債、收入、預算或帳戶簿記功能。

產品無廣告。信用卡、支付方式、交易及統計表均不限筆數，不能以固定少量筆數限制使用者建立資料。

### 1.2 產品原則

- 消費交易是核心資料；支付方式與信用卡用於描述交易，不將消費管理改造成完整帳戶記帳。
- 保留交易歷史。停用卡片或支付方式不得抹除其既有交易；刪除操作不得意外級聯刪除歷史交易。
- 匯入與還原需可預覽或驗證，並避免因無法映射而靜默遺失資料。
- 帳期、月份、日期範圍與顯示金額依實際資料及日曆動態計算，不以測試年份或固定範例日期寫死。
- APP 須以正式 Android APP 方式建置與執行；不得以直接開啟 HTML `file://` 作為正式產品交付方式。

## 2. 導覽與主要入口

主要導覽項目如下：

1. 全部消費
2. 信用卡
3. 統計表
4. 設定

APP 另須提供明確、容易找到的「新增消費」入口。入口所在位置可依 Android UI 設計安排，但不得讓使用者只能透過不明顯的隱藏手勢建立消費。

設定頁至少承載支付方式、資料匯入、備份與還原等功能；其子頁編排可依實作設計，功能不可遺漏。

## 3. 全部消費

### 3.1 清單內容

- 顯示全部支付方式的消費交易，包含現金；不得因支付方式種類而漏列交易。
- 支援月份切換，提供上一月與下一月操作。
- 交易依日期每日分組顯示。
- 顯示所選月份的總消費及交易筆數，資訊整合為單一摘要：`本月全部消費 $xxx（xx筆）`。不得同時重複顯示「本月消費 $xxx／xx筆」和「本月全部消費」兩份摘要。
- 月份左右箭頭必須能正常切換到相鄰月份：不得跳過兩個月，也不得點擊無反應。

### 3.2 月份與交易呈現

月份切換以日曆月份為單位。每日分組及月總額須依所選月份的實際交易動態產生，不能使用寫死的 2025 年日期或測試資料作為正式內容。

日期、排序、交易摘要中其他欄位的具體視覺樣式可由 Android UI 設計決定，但上述切換、每日分組、摘要和全支付方式涵蓋要求為正式行為。

## 4. 信用卡

### 4.1 卡片資料及管理

信用卡數量不限。每張卡至少包含：

- 名稱
- 末四碼
- 結帳日
- 繳款截止日
- 啟用／停用狀態

使用者可啟用或停用信用卡。停用卡片仍須保留並可供查閱其歷史交易與歷史帳期資料；停用不得等同刪除。

信用卡頁以「上月／本月」比較為主，不需要顯示下月金額。

### 4.2 帳單週期

結帳日當天即為新帳單週期第一天。帳期含第一天、不含下一週期首日，亦即以連續日期呈現時包含前一日作為本期最後一天。

結帳日為 23 日時：

- 9/23～10/22
- 10/23～11/22

帳單期須依卡片結帳日及實際交易日期動態計算，不得固定使用某個測試年份或硬編碼日期。

月份天數不足以容納結帳日（例如 29、30 或 31 日）的通用處理規則仍待確認，見第 14 節；該待確認不影響結帳日當天開啟新週期及上述 23 日範例的確定性。

## 5. 交易建立、編輯與帳期操作

### 5.1 新增及編輯

APP 支援建立消費並編輯已建立的消費。消費內容包含交易日期、整數金額、內容、備註、支付方式，以及可選的信用卡關聯；其餘確切欄位依資料模型及待確認事項處理。

「移至下月帳」只可用於已建立消費的編輯頁。新增消費頁不得出現此操作。

### 5.2 移至下月帳與移回原帳單期

- 使用「移至下月帳」時，必須實際更新交易的 `transaction_date`，將日期設為該信用卡下一個帳期的第一天，不得僅變更顯示月份、帳單期標記或篩選歸屬。
- 第一次移動時，永久保留第一次消費日期為原始消費日期。資料已記錄原始日期後，再次移動不得覆蓋它。
- 交易需保有足以辨識「移至下月帳」狀態及原始日期的資料。
- 使用者將交易移回原帳單期時，恢復第一次消費日期，並清除下月帳移動狀態。
- 上述操作須反映到全部消費、信用卡帳期及統計查詢中，不可只更新其中一個畫面。

### 5.3 複製成新消費

消費編輯頁的「複製成新消費」必須可正常操作。使用者點擊後先確認；確認後建立新交易並進入新交易編輯頁。

新交易須符合以下規則：

- 產生全新的交易 ID，絕不重用來源交易 ID。
- 交易日期設為今天，並依新日期重新計算帳單期。
- 複製信用卡、支付方式、金額、內容及備註。
- 不複製來源交易的時間戳、`source_id`、手動帳單期或下月帳狀態。
- 新交易不得更動來源交易。

### 5.4 編輯頁按鈕排版

消費編輯頁底部兩排按鈕的左右欄寬、邊界、間距與高度須一致。按鈕文字不可造成不對齊、裁切或操作區域重疊。

## 6. 支付方式

支付方式數量不限，可建立多種自訂支付方式，例如 LINE Pay、實體刷卡、網路刷卡、街口及現金。支付方式名稱不可由少數硬編碼選項限制。

現金是支付方式，不是帳戶。不得因現金沒有帳戶而將現金消費排除在全部消費、月份總額或統計之外。

支付方式停用／刪除及已關聯交易的安全規則見第 11 節。

## 7. 自訂統計表

### 7.1 統計表與篩選條件

統計表數量不限。每份統計表可組合下列條件：

- 信用卡：ALL 或指定多選
- 支付方式：ALL 或指定多選
- 日期範圍：固定區間、每月週期或跨月週期
- 目標金額

多個條件之間採 AND 關係；在同一條件種類內選取多個值時採多選符合（OR）語意。例如選取多張卡時，交易須屬於其中任一張卡，並同時符合所選支付方式與日期條件。

ALL 表示該條件種類不限制交易；選擇 ALL 時不可再以同欄位的單一選項意外排除資料。

### 7.2 日期週期

統計日期條件支援：

1. 固定起訖日區間。
2. 每月週期。
3. 跨月週期。

每月週期遇到月末時，須依該月份實際日數判定；例如目標日在該月不存在時，依該月最後一日處理，不得把某個固定測試月份或日期寫死。跨月週期的使用者設定方式與起訖點須一致呈現。

### 7.3 統計結果

使用者可查看符合條件的交易明細。結果必須依設定條件及 AND 關係篩選，並能包含所有支付方式（包括現金）。統計圖表型式、目標金額的比較運算（等於、至少或其他）、結果摘要樣式與匯出方式尚未明確指定，列為待確認事項。

## 8. Money Manager `.mmbak` 匯入

### 8.1 匯入方式與預覽

APP 支援直接匯入 Money Manager `.mmbak` SQLite 備份。匯入正式寫入前，須先提供匯入預覽，讓使用者檢視辨識到的資料與可能的映射結果。

### 8.2 交易資料保留與欄位映射

匯入須保留交易日期、金額、內容、備註、信用卡及支付方式。Money Manager 卡片欄位對應如下：

- `CARD_DAY_FIN` 對應信用卡結帳日。
- `CARD_DAY_PAY` 對應信用卡繳款截止日。

信用卡與支付方式映射須正確。不得在匯入後將原本有信用卡或支付方式的交易一律顯示為「無信用卡・未分類」。

### 8.3 未映射與重複匯入

- 不可因無法映射而默默丟棄交易。遇到無法辨識或映射失敗的資料，須在預覽或結果中明確列出並保留可處理資訊；其後續解決方式需可追蹤。
- 重複匯入時須能辨識已匯入的來源資料，避免不加辨識地重複建立相同交易。
- 匯入邏輯須保留來源識別資訊，使後續匯入可進行重複判定。

Money Manager 不同版本的 SQLite schema 差異、無法映射項目的人工處理互動，以及完整匯入衝突策略未有明確決定者，列為待確認事項。

## 9. 備份與還原

### 9.1 備份

APP 支援：

- 使用者發起的本機備份。
- Google Drive 自動備份。
- Safety Backup（安全備份），用於重要操作前保護可還原資料。

備份檔須包含：

- 資料庫內容。
- manifest（備份描述資訊）。
- checksum（完整性校驗資料）。

### 9.2 還原

還原前必須先建立 Safety Backup，並驗證待還原資料及備份完整性。備份驗證未通過時不得把不完整或損壞資料當作有效資料靜默還原。

本機備份、Google Drive 自動備份與 Safety Backup 均須納入資料保護流程。雲端登入、備份頻率、保留數量、加密與跨版本遷移細節若尚未明確決定，依第 14 節待確認事項處理。

## 10. 資料模型與完整性

以下列出 APP 所需的邏輯資料模型。欄位型別與實體關聯可依正式 Android 架構落實，但必須維持本節資料語意及完整性限制。

### 10.1 信用卡（CreditCard）

至少包含：信用卡 ID、名稱、末四碼、結帳日、繳款截止日、啟用狀態，以及建立/更新時間等必要維護資訊。停用卡片仍保留，並可關聯歷史交易。

### 10.2 支付方式（PaymentMethod）

至少包含：支付方式 ID、名稱、啟用狀態及必要維護資訊。類型需能識別現金；現金支付方式不得要求帳戶關聯。支付方式數量不限。

### 10.3 交易（Transaction）

| 欄位 | 語意 |
|---|---|
| `id` | 唯一交易 ID；複製交易時新建 |
| `transaction_date` | 目前交易日期；移至下月帳時實際更新 |
| `original_transaction_date` | 第一次消費日期；移動後永久保留，移回原帳期時用來恢復日期 |
| `amount` | 整數金額，不以浮點數儲存 |
| `content` | 消費內容 |
| `note` | 備註 |
| `credit_card_id` | 可為空的信用卡關聯；停用卡歷史交易仍可關聯 |
| `payment_method_id` | 支付方式關聯；現金也是有效支付方式 |
| 帳期移動狀態 | 表示是否已移至下月帳；須可在移回原帳期時清除 |
| 帳單期資料 | 供信用卡/統計使用；複製時不得沿用來源的手動帳期，須重新計算 |
| 時間戳 | 交易建立/更新維護資料；複製成新消費不得沿用來源時間戳 |
| `source_id` / 來源資料鍵 | 可用於匯入來源辨識與重複判斷；複製成新消費不得沿用來源交易的 `source_id` |

如需額外欄位或拆分交易表與帳期表，須保留上述行為及欄位語意。

### 10.4 統計表（StatisticsTable）與統計選擇（StatisticsSelection）

統計表資料需能保存使用者建立的多份統計設定。邏輯上至少需要：統計表識別碼/名稱、篩選條件種類、日期週期類型及起訖或週期設定、目標金額，以及對信用卡與支付方式的 ALL／多選設定。統計選擇可採關聯表或等效結構保存多選 ID；不得以固定欄位數限制選擇數量。

### 10.5 備份資料（Backup / Manifest）

備份資料需能表示資料庫備份、manifest 內容及 checksum。需辨識備份類型（本機、自動雲端或 Safety Backup）及建立時間等必要資訊；具體 manifest 格式及版本相容策略可於實作設計定義。

### 10.6 設定（Settings）

設定資料用於保存 APP 運作所需的使用者偏好與功能設定，例如統計表及備份流程所需設定。現有需求未限定設定欄位清單，新增設定不可取代或破壞上述核心資料。

### 10.7 外鍵與刪除策略

- 外鍵與刪除策略不得造成歷史交易被意外級聯刪除。
- 有關聯交易的信用卡或支付方式優先支援停用。
- 若使用者明確選擇刪除已被交易引用的信用卡或支付方式，必須在刪除前提供「保留交易」或「連同交易刪除」的明確選擇與確認。
- 執行刪除前必須建立 Safety Backup。
- 未經明確選擇及確認，不得以 cascade 等方式連帶刪除交易。

## 11. 資料安全與破壞性操作

刪除信用卡或支付方式時，如其已有關聯交易，必須清楚告知影響並讓使用者選擇保留交易或一併刪除交易。該操作完成前先建立 Safety Backup。產品操作上優先提供停用，保留歷史關聯與資料。

任何匯入、還原或刪除流程如遇到可能資料遺失，必須將影響呈現給使用者，不得靜默覆蓋或丟棄資料。

## 12. 正式 Android 架構要求

- 交付型態為正式 Android APP；不可用直接以瀏覽器開啟本機 HTML `file://` 取代正式 APP。
- 實作採用適合正式 Android APP 的原生或正式 Android 應用架構，具備清楚的 UI、領域邏輯及資料存取分層。
- 本機持久化須支援交易、信用卡、支付方式、統計設定與備份操作所需資料；完整性約束須與第 10 節一致。
- Google Drive 自動備份須以正式授權機制存取使用者雲端資料。
- 帳單週期、日期範圍、複製及匯入去重邏輯不可只存在於單一畫面暫存狀態，須可由持久化資料與領域邏輯一致地處理。

具體語言、UI toolkit、架構套件及雲端 API 由技術實作決定，須符合本節要求及各功能規格。

## 13. 正式驗收條件

### 13.1 導覽及消費

- 可從主要導覽到達全部消費、信用卡、統計表及設定。
- 有清楚可見的新增消費入口。
- 全部消費按上一月/下一月箭頭時各移動一個日曆月，無跳月或無反應。
- 全部消費依日分組、可切換月份，並以單一摘要 `本月全部消費 $xxx（xx筆）` 顯示當月總額及筆數。
- 現金及其他支付方式交易均出現在全部消費及相應總額中。

### 13.2 信用卡及帳期

- 可不限張數建立信用卡並記錄名稱、末四碼、結帳日及繳款截止日。
- 卡片可啟用/停用；停用後歷史資料與交易仍保留。
- 信用卡比較以「上月／本月」為主，不顯示下月金額。
- 結帳日 23 日的週期正確為 9/23～10/22、10/23～11/22；週期依實際資料動態計算。

### 13.3 移動與複製交易

- 新增消費頁沒有「移至下月帳」；已建立交易的編輯頁提供此操作。
- 執行移動後 `transaction_date` 實際等於下一帳期首日。
- 初次移動保留原始日期；重複移動不覆寫；移回時恢復原始日期並清除移動狀態。
- 複製成新消費先要求確認；確認後建立新 ID、新交易並開啟該筆新交易編輯頁。
- 新交易日期為今天，信用卡、支付方式、金額、內容、備註均依來源複製，帳期重新計算；ID、時間戳、`source_id`、手動帳期、下月帳狀態不沿用。
- 編輯頁底部兩排按鈕左右欄寬、邊界、間距及高度一致。

### 13.4 支付方式及統計表

- 可建立不限數量的支付方式；現金不要求帳戶。
- 可建立不限數量統計表，配置信用卡、支付方式、日期範圍及目標金額。
- 信用卡與支付方式支援 ALL 及指定多選；不同條件種類之間採 AND。
- 日期條件支援固定區間、每月週期及跨月週期；月末依實際日數計算。
- 使用者可開啟統計結果中的符合條件交易。

### 13.5 匯入、備份與資料安全

- 可選取 `.mmbak` 並在寫入前預覽；交易日期、金額、內容、備註、信用卡及支付方式正確保留。
- `CARD_DAY_FIN` 映射為結帳日，`CARD_DAY_PAY` 映射為繳款截止日。
- Money Manager 匯入後不得把可識別的卡片/支付方式交易全部降為「無信用卡・未分類」。
- 不可映射的交易或資料須明確呈現並保留，不得靜默丟棄；重複匯入可辨識既有來源資料。
- 可建立本機備份、Google Drive 自動備份及 Safety Backup；備份包含資料庫、manifest、checksum。
- 還原前建立 Safety Backup 並驗證資料。
- 刪除有關聯資料的信用卡或支付方式前建立 Safety Backup，並取得保留交易或連同刪除交易的明確選擇。

### 13.6 版本與日期品質

- 正式使用者介面不得殘留 V0.9 等舊測試版本文字。
- 不得出現寫死的 2025 年測試日期。
- 帳期、月份、統計日期區間依實際日期和資料動態計算。
